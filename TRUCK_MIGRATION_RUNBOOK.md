# Truck backup, migration and recovery

Take the application offline for all truck writes before starting, including scheduled jobs, older deployments and scripts. The maintenance control is enforced only by versions of writers that read `shops/{shop}/truckControl/main` in the same transaction as their write. Do not restore while older versions or direct Firestore writers can run. Backup is not a point-in-time Firestore snapshot: quiesce writers before export.

1. Run `npm run backup`, retain the resulting JSON securely, and run `npm run restore-check -- <backup.json>`. Confirm the target shop and totals and keep the original unchanged. Photos stored as Firestore documents are included; separately back up any external storage objects, since a URL is not the photo bytes.
2. Run `npm run truck:migration:preview -- <backup.json> <preview.json>` and compare record counts, trip counts, total driver pay and photo references to the legacy source. Resolve mismatches before continuing. No historical base wage, customer, driver identity, billing price, time or delivery date is inferred.
3. Run `npm run truck:migration:import -- <backup.json> --apply` against the intended shop. Deterministic IDs and create-only transactions make retries safe; existing differing candidates or closed payroll months stop the import. A failure may occur after earlier candidates were created: fix the cause and rerun the identical backup. Imported trips require manual review before financial use.
4. For recovery, restore only into an empty truck namespace: `npm run truck:restore -- <backup.json> --apply`. The checksum and shop ID must match. The command acquires `truckControl/main` maintenance, checks the target, then creates all documents and clears maintenance in one transaction. Backups above 450 truck documents are rejected rather than partially restored. Use an isolated project and a verified administrative recovery procedure for larger datasets.
5. An interrupted or rejected restore leaves maintenance active; retry the same backup after correcting the problem. If abandoning recovery, investigate the target and clear the maintenance flag only after an administrator has verified no partial or conflicting data exists. Never clear it while a restore is running. After restoration compare counts, totals, snapshots and photo contents, then bring the application back online.

The browser backup endpoint is an informational export, not the checksummed CLI backup. Browser restore is disabled. Firestore collection queries do not discover orphan subcollections under missing parent documents; inspect the destination for orphans before restore. This procedure does not restore attendance data or external photo objects. Firestore native non-JSON types require a native Firestore export: the JSON backup should be used only when stored values are JSON-compatible.
